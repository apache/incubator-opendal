18//! Implementing a service.
19//!
20//! Every OpenDAL backend implements the raw [`Service`] trait. A service owns
21//! protocol-specific request construction and response handling. The operator
22//! owns path normalization, option validation, layer composition, and
23//! dispatch.
24//!
25//! Service crates live under `core/services/<name>/`. Their public builder and
26//! configuration types construct a typed backend; the backend then implements
27//! [`Service`].
28//!
29//! # Service identity and capabilities
30//!
31//! [`Service::info`] returns immutable identity such as the scheme, root, and
32//! namespace name. Runtime resources do not belong in [`ServiceInfo`];
33//! services read them from [`OperationContext`].
34//!
35//! [`Service::capability`] reports the behavior implemented by that service
36//! stack. Set an operation or option capability only when the implementation
37//! satisfies the corresponding public contract. Operators reject options whose
38//! required capability is absent.
39//!
40//! # Operation body types
41//!
42//! [`Service`] uses associated types for operation bodies:
43//!
44//! ```text
45//! type Reader: oio::Read;
46//! type Writer: oio::Write;
47//! type Lister: oio::List;
48//! type Deleter: oio::Delete;
49//! type Copier: oio::Copy;
50//! type Composer: oio::Compose;
51//! ```
52//!
53//! A backend returns concrete body types so its implementation and typed
54//! wrappers do not pay for dynamic dispatch. Use `()` for an unsupported body
55//! type and return [`ErrorKind::Unsupported`] from the corresponding operation
56//! entry point.
57//!
58//! OpenDAL erases these types once, at [`ServiceDyn`]. [`Servicer`] is
59//! `Arc<dyn ServiceDyn>` and is the handle used by operators and runtime layer
60//! composition. A wrapper that receives a [`Servicer`] may forward erased
61//! `oio::*` bodies, but a backend should keep its own bodies concrete.
62//!
63//! # Operation methods
64//!
65//! Each operation method receives normalized paths, an [`OperationContext`],
66//! and operation-specific arguments. The context supplies layer-composed
67//! runtime resources such as the HTTP transport and executor. Options such as
68//! ranges, versions, conditions, and concurrency remain in the operation
69//! arguments.
70//!
71//! An implementation must:
72//!
73//! - Map every advertised option to the native request without silently
74//!   dropping it.
75//! - Preserve the operation's public success, error, and atomicity contract.
76//! - Return structured OpenDAL errors with the correct [`ErrorKind`] and
77//!   useful context.
78//! - Keep credentials and other secrets out of `Debug` output and errors.
79//! - Forward cancellation and cleanup to protocol-specific readers, writers,
80//!   deleters, and copiers.
81//!
82//! # Adding or changing a service
83//!
84//! Keep configuration, request construction, operation bodies, and error
85//! parsing at their existing service boundaries. Update the facade feature and
86//! service registration when the service must be available through the
87//! `opendal` crate.
88//!
89//! Before advertising new behavior, reproduce it against the actual service
90//! and run the matching capability-gated behavior tests. Protocol
91//! documentation, emulators, and fabricated responses can explain an
92//! implementation, but they do not establish real-service conformance.
